# School Management System SaaS — Security Release Checklist

> [!CAUTION]
> **Release Gate Policy**: This application processes sensitive personal, academic, and financial records of minors (students), parents/guardians, and faculty. **No release may be approved for real school or student data while any Critical security requirement remains unresolved (`NOT ASSESSED`, `IN PROGRESS`, or `BLOCKED`).**

## 0. Release Readiness Summary & Gate Classification

### Current Release Gate Status: **NOT READY**

Based on a comprehensive inspection of the current codebase (`backend/` and `frontEnd/`), the application is currently an unauthenticated, single-tenant MVP prototype backed by a local H2 file database (`jdbc:h2:file:./data/school_management`). While strong foundations exist for frontend runtime schema validation ([`apiValidator.js`](file:///Users/miessanhenri/Developer/Projects/School_Mangement/frontEnd/js/utils/apiValidator.js)), DOM XSS prevention (`createElement` / `textContent`), and parameterized JPA queries ([`StudentRepository.java`](file:///Users/miessanhenri/Developer/Projects/School_Mangement/backend/src/main/java/com/miessan/schoolmanagement/repository/StudentRepository.java)), core SaaS security controls have not yet been architected or implemented.

## Rules for Updating Checklist Status

Allowed status values:
- `NOT ASSESSED`: Requirement has not yet been tested or cannot be tested because the underlying feature/architecture is not yet implemented.
- `IN PROGRESS`: Implementation or testing is actively underway, or partial controls exist without full test coverage.
- `VERIFIED`: The control is fully implemented **and** backed by passing automated tests or documented verification artifacts.
- `BLOCKED`: Cannot proceed until an upstream architectural, legal, or infrastructure decision is finalized.
- `NOT APPLICABLE`: Formally determined not to apply to the chosen architecture (must include justification in Notes).

### Evidence Required Before Marking Any Item `VERIFIED`
A requirement **must never** be marked `VERIFIED` merely because a dependency exists in [`backend/pom.xml`](file:///Users/miessanhenri/Developer/Projects/School_Mangement/backend/pom.xml) or code compiles. Moving an item to `VERIFIED` requires:
1. **Exact Code Reference**: File path and line numbers of the security configuration, filter, annotation, or validator.
2. **Automated Negative & Positive Test Evidence**: Passing JUnit 5 / `MockMvc` integration test class and method name (or Playwright E2E spec) demonstrating both authorized success (`200`/`201`) and unauthorized/malicious rejection (`400`/`401`/`403`/`404`).
3. **Configuration/Infrastructure Artifact**: Where infrastructure is involved (TLS, backups, secrets, Docker), the exact configuration file, script, or dated operational test log must be linked.

## 4. School / Tenant Data Isolation

> **Architectural Decision Required (`ARCH-TENANT-01`)**: Multi-tenancy has **not** yet been designed or implemented. Before onboarding real schools, the engineering team must formally select and document the multi-tenancy model:
> 1. **Shared Database, Shared Schema with Discriminator Column (`school_id`)** + Hibernate `@TenantId` / PostgreSQL Row-Level Security (RLS),
> 2. **Shared Database, Separate Schema per School**, or
> 3. **Database-per-School**.
